# Setup Guide

All runtime data files (images, CSV tables, soil data, yield data) are hosted on **OSF** (Open Science Framework) and **Zenodo** and must be downloaded before the API can serve requests. Both sources contain the same files — choose whichever works best for you.

---

## Automated Setup (recommended)

The `setup.sh` script handles everything: system packages, R packages, Python tooling, and data download.

```bash
chmod +x setup.sh
./setup.sh
```

Options:

```bash
./setup.sh --no-system   # skip apt-get (manage system packages yourself)
./setup.sh --no-data     # skip data download (do it later)
```

The script targets **Debian/Ubuntu**. For other distros, pass `--no-system` and install the [system packages](#system-packages) manually before running.

## Manual Setup

### System packages

**Debian/Ubuntu:**

```bash
sudo apt-get update
sudo apt-get install -y \
  libnetcdf-dev libhdf5-dev \
  libpango-1.0-0 libpangoft2-1.0-0 libgdk-pixbuf2.0-0 \
  libfreetype6-dev libpng-dev libtiff5-dev libjpeg-dev \
  libssl-dev libcurl4-openssl-dev libxml2-dev \
  libgdal-dev libgeos-dev libproj-dev libudunits2-dev libabsl-dev cmake
```

**Purpose:**

| Package | Required by |
|---------|------------|
| `libnetcdf-dev`, `libhdf5-dev` | ncdf4 R package — reads yield raster data |
| `libpango-1.0-0`, `libpangoft2-1.0-0`, `libgdk-pixbuf2.0-0` | WeasyPrint — PDF rendering (font layout, image support) |
| `libfreetype6-dev`, `libpng-dev`, `libtiff5-dev`, `libjpeg-dev` | ragg — headless PNG rendering for ggplot2 charts (no X11 required) |
| `libssl-dev`, `libcurl4-openssl-dev` | httr R package — HTTP requests |
| `libxml2-dev` | xml2 R package (dependency of several packages) |
| `libgdal-dev`, `libgeos-dev`, `libproj-dev` | sf R package — builds the `GET /coverage` footprints |
| `libudunits2-dev` | units R package (dependency of sf) |
| `libabsl-dev`, `cmake` | s2 R package (dependency of sf); `cmake` lets s2 build Abseil itself if `libabsl-dev` is unavailable |

> `install_packages.R` exits with an error if any required R package fails to install, so a deploy stops before restarting the API. Check its output for the missing system library.

> **Headless servers:** The API generates ggplot2 charts (PP and SP recommendation matrices) at runtime. The `ragg` R package is used as the rendering backend — it requires no X11 display and produces higher-quality output than the default PNG device. The system libraries above (`libfreetype6-dev` etc.) are its build-time dependencies. If `ragg` is unavailable, the server falls back to Cairo (`options(bitmapType="cairo")`), which also works headless as long as `libcairo2` is present.

### WeasyPrint (PDF renderer)

PDF reports are generated by [WeasyPrint](https://weasyprint.org) — a Python-based HTML/CSS → PDF converter. Install it before starting the API. Install from `requirements.txt` (run the commands below from the repo root; the version is not pinned, so pip gets the latest); do not use the distro `python3-weasyprint` package, which is older.

**Linux (system-wide — recommended for production services):**
```bash
# System libraries required by WeasyPrint (font layout + image support)
sudo apt-get install -y libpango-1.0-0 libpangoft2-1.0-0 libgdk-pixbuf2.0-0

# Install WeasyPrint system-wide
sudo pip3 install -r requirements.txt

# On Debian 12+ / Ubuntu 23.04+ pip refuses to install outside a venv by default.
# Override with --break-system-packages (safe for server deployments):
sudo pip3 install --break-system-packages -r requirements.txt

weasyprint --version   # verify
```

Installing system-wide (`sudo pip3`) places the binary in `/usr/local/bin`, which is on the default `PATH` for systemd services. Installing per-user (`pip install --user`) places it in `~/.local/bin`, which systemd does **not** include by default — see [Production deployment (systemd)](#production-deployment-systemd) below.

**macOS:**
```bash
pip install -r requirements.txt
weasyprint --version
```

**Windows (development):**
```powershell
pip install -r requirements.txt
# GTK runtime also required — install from:
# https://github.com/tschoonj/GTK-for-Windows-Runtime-Environment-Installer
weasyprint --version
```

See [WEASYPRINT-WINDOWS.md](WEASYPRINT-WINDOWS.md) for a detailed Windows walkthrough.

### R packages

Run the provided installer script — works on Linux, macOS, and Windows:

```bash

```

This installs all required packages and checks that WeasyPrint is on `PATH`. Java is not needed: this service does not send email (the AKILIMO API sends the PDF).

### Environment configuration

There are two separate `.env` files — one per subsystem:

| File | Used by | Copy from |
|------|---------|-----------|
| `.env` (project root) | R API — server binding and options | `.env.example` |
| `scripts/.env` | Python data scripts — OSF/Zenodo IDs and tokens | `scripts/.env.example` |

```bash
# R API config
cp .env.example .env

# Python / OSF / Zenodo config
cp scripts/.env.example scripts/.env
```

Neither file is committed (both matched by `.gitignore`).

**Key variables in `.env`:**

| Variable | Default | Description |
|----------|---------|-------------|
| `AKILIMO_ROOT` | `.` | Absolute path to project root |
| `API_HOST` | `0.0.0.0` | Plumber listen address |
| `API_PORT` | `8000` | Plumber listen port |
| `AKILIMO_DB_PATH` | `data/input/akilimo_compute.sqlite` | Path to the SQLite price database |
| `AKILIMO_API_URL` | — | Base URL of the external price service (unset = auto-refresh disabled) |
| `AKILIMO_API_TOKEN` | — | Bearer token for the price API |
| `PRICE_MAX_AGE_DAYS` | `7` | Days before fertilizer/cassava prices trigger an auto-refresh |
| `PRICE_FULL_SYNC_HOURS` | `24` | Hours between full price fetches, which also remove prices the service has deactivated (a refresh in between fetches only what changed; `refresh_prices.R --full` forces one) |
| `STARCH_PRICE_MAX_AGE_DAYS` | `30` | Days before starch factory prices trigger an auto-refresh |

### Price database (SQLite)

Fertilizer, labour, cassava, and starch factory prices are stored in a local
SQLite file (`data/input/akilimo_compute.sqlite`). The file is created automatically on
first server start — seeded from the bundled CSV files — and updated via the
refresh script below.

#### Manual price refresh

Use `refresh_prices.R` to pull the latest prices from the configured
`AKILIMO_API_URL` and write them into the database:

```bash
# Refresh everything (all countries, both price types)
Rscript refresh_prices.R

# Refresh fertilizer/labour/cassava prices for Nigeria only
Rscript refresh_prices.R --country NG --type default

# Refresh starch factory prices for all countries
Rscript refresh_prices.R --type starch

# Validate what the API would return without writing to the DB
Rscript refresh_prices.R --dry-run
```

`AKILIMO_API_URL` must be set in `.env` before running. If it is not set, the
script exits with an error immediately.

#### Scheduled refresh (cron)

To keep prices current automatically, add a cron job on the server. Example —
refresh all prices every Monday at 02:00:

```cron
0 2 * * 1  cd /opt/akilimo && Rscript refresh_prices.R >> logs/price-refresh.log 2>&1
```

Adjust the schedule to match how frequently your price source publishes updates.

#### Auto-refresh during requests

When `AKILIMO_API_URL` is set, the API server also checks price freshness on
each incoming request (after parsing, before computing). If prices are older
than `PRICE_MAX_AGE_DAYS` (default 7), a background refresh runs silently.
A failed auto-refresh is logged as WARN and never blocks the recommendation.

See [docs/TECH-DEBT.md § SQLite price database](TECH-DEBT.md#sqlite-price-database-datainputakilimo_computesqlite) for the database schema and API contract reference.

### Download runtime data

The data is available from two sources — **OSF** (default) and **Zenodo**. Both contain identical files.

```bash
cd scripts

# OSF (default — no token required for public projects)
poetry run setup-data
poetry run setup-data --source osf --osf-node-id rcjv5

# Zenodo (alternative)
poetry run setup-data --source zenodo
poetry run setup-data --source zenodo --zenodo-id 19231022
poetry run setup-data --source zenodo --sandbox   # sandbox.zenodo.org
```

Everything in the data folder is bundled: each folder directly under `data/` is one asset with its own archive (`data/<name>` is `<name>-data.tar.gz`), found automatically, so a new data folder needs no configuration. What is **not** bundled is the exclusion list in `scripts/assets.json` (hidden folders, `*.sqlite` and the other price-database files, and the files tracked in git such as `translations.csv`); an extraction never overwrites those either. Today:

| Asset | Bundle | Extracted to | Contents |
|-------|--------|-------------|----------|
| `input` | `data-input.tar.gz` | `data/input/` | CSV lookup tables (prices, defaults) |
| `soil` | `soil-data.tar.gz` | `data/soil/` | Soil NPK RDS files |
| `yield` | `yield-data.tar.gz` | `data/yield/` | Yield NetCDF rasters (LINTUL model) |
| `dssat` (optional) | `dssat-data.tar.gz` | `data/dssat/` | DSSAT planting date x cultivar output (PDC, Nigeria maize) |
| `spam` (optional, on demand) | `spam-data.tar.gz` | `data/spam/` | MapSPAM 2020 source for the cassava-area mask (109 MB); not downloaded unless asked: `setup-data --only spam` |

Choose which assets a run handles; the same options work for `bundle-assets`, `upload-osf` and `upload-zenodo`:

```bash
poetry run setup-data --list-assets          # names, folders, and what is selected
poetry run setup-data --only soil --only yield
poetry run setup-data --exclude dssat        # e.g. a server that never serves PDC
```

To make a choice permanent, set `ASSETS` (exactly these) or `ASSETS_EXCLUDE` in `scripts/.env`. `required` in `assets.json` names the assets whose absence fails a run; every other asset is optional and is skipped with a warning when it is not published yet. To keep something out of the bundles, add a pattern to `exclude` (gitignore style: a name without `/` matches anywhere, a pattern with `/` matches that path). With a published manifest, `setup-data` also fetches assets it lists that this repository has never heard of. If OSF answers 401, set `OSF_TOKEN` (in `scripts/.env` or the environment); it is sent to `api.osf.io` and `files.osf.io` only. For a private project the token must allow reading file contents as well as listing them (a download without it is a login page, which `setup-data` now reports as "not a gzip file").

The Data setup workflow has matching `assets` and `exclude_assets` inputs.

Re-running is safe — already-extracted files are preserved.

## Production deployment (systemd)

The API runs as a systemd service under a dedicated `akilimo` user. Two service templates are provided — one for production and one for the beta instance.

| Instance | Branch | Directory | Service | Port |
|----------|--------|-----------|---------|------|
| Production | `main` | `/home/akilimo/projects/new_akilimo` | `akilimo-api.service` | 8000 |
| Beta | `experimental` | `/home/akilimo/projects/akilimo-beta` | `akilimo-api-beta.service` | 8001 |

> The folder the deploy updates is `app_dir` in `.github/deploy-targets.json`, which is the source of truth: the paths in this section are examples. The service's `WorkingDirectory` must be that same folder, because the API reads `.env` (including `API_PORT`) from the folder it starts in. Beta's port comes from `API_PORT=8001` in that `.env`; the unit file does not set it. To check a server: `sh tools/check_service.sh beta`.

### Install or update the production service

```bash
# Copy template to systemd drop-in directory
sudo cp systemd/akilimo-api.service.example /etc/systemd/system/akilimo-api.service

# Edit paths/user to match your server layout
sudo nano /etc/systemd/system/akilimo-api.service

# Reload systemd and start
sudo systemctl daemon-reload
sudo systemctl enable akilimo-api
sudo systemctl start akilimo-api
sudo systemctl status akilimo-api
```

### Install or update the beta service

```bash
# Clone the repo into the beta directory (first time only)
git clone <repo-url> /home/akilimo/projects/akilimo-beta
cd /home/akilimo/projects/akilimo-beta
git checkout experimental

# Configure a separate port
cp .env.example .env
# edit .env: API_PORT=8001

# Install the service
sudo cp systemd/akilimo-api-beta.service.example /etc/systemd/system/akilimo-api-beta.service
sudo nano /etc/systemd/system/akilimo-api-beta.service

sudo systemctl daemon-reload
sudo systemctl enable akilimo-api-beta
sudo systemctl start akilimo-api-beta
sudo systemctl status akilimo-api-beta
```

### WeasyPrint PATH under systemd

Systemd services run with a minimal `PATH` (`/usr/bin:/bin`) — it does **not** include the interactive-shell additions from `~/.bashrc` or `~/.profile`. This means that if WeasyPrint was installed with `pip install --user -r requirements.txt` by a different user, the service will not find it and every PDF request will fail with *"error in running command"*.

**Recommended approach — install system-wide:**

```bash
# Install system-wide (binary goes to /usr/local/bin)
sudo pip3 install -r requirements.txt

# On newer Debian/Ubuntu systems that block pip outside a virtualenv,
# use the --break-system-packages flag:
sudo pip3 install --break-system-packages -r requirements.txt

# Confirm the binary is on a system path
which weasyprint
# → /usr/local/bin/weasyprint

# Verify it works as the service user
sudo -u akilimo weasyprint --version
```

No service file changes are needed — `/usr/local/bin` and `/usr/bin` are already in the default systemd `PATH`.

**Alternative — per-user install with explicit PATH:**

```bash
# Install as the akilimo user
sudo -u akilimo pip install --user -r requirements.txt

# Confirm the install path
sudo -u akilimo which weasyprint
# → /home/akilimo/.local/bin/weasyprint

# Add to the service PATH (edit the service file or use an override):
sudo systemctl edit akilimo-api
```
Override content:
```ini
[Service]
Environment=PATH=/home/akilimo/.local/bin:/usr/local/bin:/usr/bin:/bin
```
Then `sudo systemctl daemon-reload && sudo systemctl restart akilimo-api`.

**Verify WeasyPrint is reachable by the service user:**

```bash
sudo -u akilimo weasyprint --version
```

At startup, the API logs either:
```
[INFO]  WeasyPrint: weasyprint 62.3
```
or:
```
[ERROR] WeasyPrint not found — PDF generation will fail.
```
Check with `journalctl -u akilimo-api --since "1 min ago"`.

### Required writable directories

The systemd unit uses `ProtectSystem=strict`, which makes the entire filesystem read-only except for paths listed in `ReadWritePaths`. The following paths must be writable:

| Path | Purpose |
|------|---------|
| `<project>/temp/` | Per-request temp directory — HTML and PDF intermediates for WeasyPrint |
| `<project>/data/` | SQLite price database (`akilimo_compute.sqlite` is written here) |
| `<project>/logs/` | Application log files |

Create them if they don't exist and set ownership to the service user:

```bash
cd /home/akilimo/projects/akilimo-recommendations
mkdir -p temp data/input logs
chown -R akilimo:akilimo temp data logs
```

If `temp/` is not writable, WeasyPrint will have nowhere to write the HTML input file and every PDF generation attempt will fail silently.

### View logs

```bash
# Live tail
journalctl -u akilimo-api -f

# Last 200 lines
journalctl -u akilimo-api -n 200

# Filter by level (logs include [INFO], [WARN], [ERROR] prefixes)
journalctl -u akilimo-api | grep ERROR
```

## Maintainer: Publishing Data Updates

### 1. Bundle the data directories

```bash
cd scripts
poetry run bundle-assets
# Produces one dist/<archive> per asset in scripts/assets.json
```

Bundle specific assets only:

```bash
poetry run bundle-assets --only soil --only yield
poetry run bundle-assets --exclude dssat
poetry run bundle-assets --interactive      # shows files and size per asset, then asks one by one
```

Bundling also writes `dist/manifest.json` (schema 2): for each bundled asset its archives (an asset is one archive, plus one extra archive for each file over `split_over_mb`, 50 MB by default, so changing one big file re-uploads only that file), and for each archive its SHA-256, size and the exact files inside, plus the generation time and git commit. Sizes are bytes, and also text (`"1.4 MiB"`) unless you pass `--no-human-sizes` or set `human_sizes` to false in `assets.json`. Archives of files that are already compressed (`.rds`, `.zip`, ...) are stored without recompressing; the rest use gzip level 6. A partial run keeps the entries of assets bundled earlier whose archive is still in `dist/`. `upload-osf` and `upload-zenodo` upload the manifest with the bundles. Archives are reproducible (sorted members, no timestamps or owners), so bundling unchanged data gives the same hash, and an upload skips any file the host already holds with the same hash (OSF compares SHA-256, Zenodo MD5; the manifest itself is only rewritten when its contents change). `--force` uploads everything anyway. Uploads run 3 files at a time (`--jobs N`, 1 to 8), read the file in 1 MiB blocks, wait longer for bigger files, and retry a dropped connection or a 429/5xx answer with a growing pause (OSF and Zenodo cannot resume, so a retry restarts that file). Every successful upload is recorded at once in `dist/upload-state.json` (per target: the OSF node or Zenodo deposit, with the file's SHA-256), so after a crash, Ctrl-C or a failed file the next run skips what already went up and sends only the rest; a rebuilt archive with different content goes again, and `--force` ignores the record. The manifest is uploaded last, and only when every archive went up. `assets.json` has two pattern lists with the same syntax: `exclude` (whole folders and files that belong to the repo or the server) and `ignore` (junk inside the folders being bundled: `*.tmp`, `*.bak`, `*~`, `Thumbs.db`, `desktop.ini` by default). To leave files out of one bundling run, use `--ignore PATTERN` (repeatable, relative to `data/`, e.g. `--ignore 'yield/*.bak' --ignore 'soil/old'`), or set `ASSETS_IGNORE` for good.

`setup-data` reads the published manifest first. With it, every download is checked against its SHA-256, only the files the manifest lists are extracted, and a required asset missing from the manifest fails early with a clear message. Without one (older publishes) it falls back to the asset registry alone. `--no-manifest` ignores it.

### GitHub Releases: a third place to keep the data

**GitHub is the default source of the data.** `poetry run upload-github` publishes the archives and `manifest.json` as assets of one release of the private data repository named in `scripts/assets.json` (`github.repo`, `IITA-AKILIMO/akilimo-data`), and plain `poetry run setup-data` downloads them. The default source (`default_source`) and the repository and tag can be changed in that file; `--source osf` or `zenodo`, or the `DATA_SOURCE` variable, use another host. Assets can be up to 2 GiB, which the 50 MB split stays far under.

| Setting | Meaning |
|---|---|
| `GITHUB_DATA_TAG` | the release tag, default `data-latest`; a dated tag such as `data-2026-11-23` keeps a release of its own. The release is created as a pre-release that is never marked "latest", so it does not interfere with the version releases of the deploy |
| `GITHUB_DATA_REPO` | `owner/name`; default `GITHUB_REPOSITORY` in Actions, else this checkout's `origin` |
| `GITHUB_TOKEN` or `GH_TOKEN` | needed to upload (it can write releases) and, for a private repository, to download (it can read contents); empty falls back to the GitHub CLI's login (`gh auth login`). Sent to `api.github.com` and `uploads.github.com` only |

Uploads behave like the other hosts: files whose SHA-256 GitHub already holds are skipped (GitHub reports one per asset), a changed asset is deleted and uploaded again, the upload ledger and `--jobs` and `--force` apply, and the manifest goes last. Downloads are verified against the manifest, or against GitHub's own SHA-256 when there is no manifest.

**The data stays out of the public code repository:** the release lives in the separate private repository `IITA-AKILIMO/akilimo-data`. Upload with `poetry run upload-github` (it needs your token: `GITHUB_TOKEN` or `gh auth login`). Everything that downloads needs a token that can read that repository, because the job's own token reads only the code repository: create a fine-grained personal access token with **Contents: read** on `akilimo-data` and store it as the `DATA_GITHUB_TOKEN` secret (CI, Deploy and Data setup all use it). The repository variables `DATA_REPO` and `DATA_TAG` override the repository and tag of `assets.json`, and `DATA_SOURCE=osf` (or `zenodo`) takes CI and the servers back to that host. CI also falls back to OSF, with a warning, if the default source fails (the release is not published yet, the token is missing, GitHub is down); the servers' data pull does not, so a failure there is loud.

If the manifest cannot be read because the host fails (not because none is published), `setup-data` stops with a message instead of guessing the archives from the registry; an asset split into several archives would come out incomplete. `--no-manifest` downloads each asset's main archive only. Downloads retry transient errors (six tries, about two minutes).

### 2. Upload — choose OSF or Zenodo

#### Option A: OSF (recommended)

Add your token to `scripts/.env`:

```dotenv
OSF_TOKEN=your-personal-access-token   # scope: osf.full_write
```

First upload — creates a new project:

```bash
poetry run upload-osf --new
# Prints node ID — save it as OSF_NODE_ID in .env
```

Update an existing project:

```bash
poetry run upload-osf                          # uses OSF_NODE_ID from .env
poetry run upload-osf --node-id abc12          # or pass explicitly
```

Test against the OSF sandbox first:

```bash
poetry run upload-osf --new --sandbox
```

After upload, open the project URL, adjust metadata, and make the project **public** to allow unauthenticated downloads.  
Update `scripts/.env` and `scripts/.env.example` with the node ID:

```dotenv
OSF_NODE_ID=rcjv5
```

#### Option B: Zenodo

Add your token to `scripts/.env`:

```dotenv
ZENODO_TOKEN=your-personal-access-token   # scope: deposit:write
```

First upload — creates a new deposit:

```bash
poetry run upload-zenodo --new
# Prints deposit ID — save it as ZENODO_DEPOSIT_ID in .env
```

Update an existing draft:

```bash
poetry run upload-zenodo                           # uses ZENODO_DEPOSIT_ID from .env
poetry run upload-zenodo --deposit-id 1234567      # or pass explicitly
```

Test against the sandbox first:

```bash
poetry run upload-zenodo --new --sandbox
```

### 3. Publish and update the record ID (Zenodo)

1. Open the deposit URL printed after upload.
2. Review metadata and click **Publish**.
3. Copy the published **Record ID** and update `scripts/.env` and `scripts/.env.example`:

```dotenv
ZENODO_RECORD_ID=<new-record-id>
```

Also update the record ID in this file and in `setup.sh` so other users download the correct version.
