## 2. PDF Pipeline — WeasyPrint Replaces R Markdown

**Decision required:** This is the single largest change. Eight `.Rmd` templates are deleted; all PDF rendering moves to pure HTML → WeasyPrint.

### What changed
- All recommendation PDFs (FR, IC, PP, SP, CIS in Swahili and English) are now generated by `R/pdf_builders.R` functions: `build_fr_pdf()`, `build_ic_pdf()`, `build_pp_pdf()`, `build_sp_pdf()`
- HTML is assembled from fragment helpers in `R/html_helpers.R` (e.g. `html_open()`, `html_personal_info()`, `html_star_rating()`)
- Assets (banner, bag PNGs, chart PNGs, map PNG) are embedded as **base64 data URIs** — no external file dependency at render time
- WeasyPrint renders HTML → PDF via `system2("weasyprint", ...)`
- PDF failures are **isolated per recommendation type** — one failure does not suppress the JSON response or other PDFs
- New CSS files: `net/akilimo.css`, `net/akilimo_print.css`
- New image assets: `net/blue/`, `net/green/`, `net/grey/`, `net/orange/`, `net/purple/`, `net/red/`, `net/redMG/`, `net/royal/`, `net/yellow/`, `net/cash/`, `net/Akilimo_Dashboard_*.png`

### Why this matters
- Removes dependency on `knitr`/`rmarkdown`/`pandoc`/`wkhtmltopdf`
- WeasyPrint is pure Python (`pip install weasyprint`) — no browser or Java required
- Requires Python + WeasyPrint on the server; `setup.sh` handles installation

## 3. API & Validation

### `R/AkilimoMain.R` — complete rewrite of `run_akilimo()`
- **`validate_request(body)`** — new function enforcing:
  - `country` must be one of `c("NG", "TZ", "RW", "GH", "BI")`
  - Country normalised to uppercase before check (was silently broken before)
  - `lat`/`lon` must be numeric and in valid range
  - `area` must be a positive number
  - `areaUnits` must be one of `c("ha", "acre", "are", "m2")`
  - At least one recommendation flag (`FR`, `IC`, `PP`, `SPP`, `SPH`) must be `TRUE`
  - `FCY` must be 0–100 t/ha if provided
  - `PD`/`HD` must be valid `YYYY-MM-DD` dates if provided
  - `PD_window`/`HD_window` must be non-negative integers
- **`bad_request(msg)`** helper returns a consistent `{status, version, data}` envelope for 400 errors
- **Unified response envelope** — all responses (success and error) now return `{status, version, data}` (was inconsistent)
- `AKI_VERSION` pulled from `misc.R` constant, not inline string

### Response format change (breaking)
Old error response: `list(status = "404 - bad request", data = NULL)`  
New response: `list(status = "400 - bad request", version = AKI_VERSION, data = list(message = "..."))`

### 1. WeasyPrint PDF Pipeline
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** Replace all 8 R Markdown (`.Rmd`) templates and the knitr/pandoc/wkhtmltopdf toolchain with a pure HTML → PDF pipeline rendered by WeasyPrint (Python).

**Why it's better:** Removes a fragile multi-tool dependency chain (knitr + pandoc + wkhtmltopdf). WeasyPrint is installed with a single `pip install weasyprint` and works headlessly with no browser or Java. PDF failures are now isolated per recommendation type — one broken PDF no longer suppresses the JSON response.

**Tradeoff / risk:** Adds a Python runtime dependency to the server. PDF visual output will differ from the Rmd templates — someone needs to sign off that the new layout is acceptable for all recommendation types (FR, IC, PP, SP) and both locales (English, Swahili). The new CSS lives in `net/akilimo.css` and `net/akilimo_print.css`.

**Questions for team:**
- Do we have a sample output to compare against the old Rmd PDFs?
- Is Python already available on the production server, or does `setup.sh` need to be run first?

### 2. SQLite Data Layer (Prices & Translations)
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** Replace direct CSV reads for `Default_prices.csv`, `starchPrices.csv`, and `translations.csv` with a local SQLite database (`data/input/akilimo_compute.sqlite`) that auto-refreshes from the remote API when data is stale.

**Why it's better:** Prices and translations can now be updated without redeploying the service. Staleness windows are configurable via env vars (`PRICE_MAX_AGE_DAYS`, `STARCH_PRICE_MAX_AGE_DAYS`, `TRANSLATIONS_MAX_AGE_DAYS`). A `price_refresh_log` audit table records every refresh. Manual refresh is available via `Rscript refresh_prices.R`.

**Tradeoff / risk:** First boot on a fresh server must seed the database from the CSV files. If `AKILIMO_API_URL` is not set, auto-refresh is skipped and the seed data is used indefinitely. Existing deployments with a different schema version will be migrated automatically by `migrate_akilimo_db()` — but this should be tested against a copy of the production database before going live.

**Questions for team:**
- Is `AKILIMO_API_URL` already configured in production?
- Do we want the auto-refresh to run on every request, or move it to a scheduled job instead?

### 3. Unified API Response Envelope
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** All `/compute` responses — success and error — now return a consistent `{status, version, data}` envelope. Error responses previously returned `{status: "404 - bad request", data: null}`; they now return `{status: "400 - bad request", version: "...", data: {message: "..."}}`. HTTP status codes are also set correctly (400 vs 500) instead of always returning 200.

**Why it's better:** Consumers can reliably parse every response with the same schema. The `version` field in every response makes it easy to correlate logs with a deployed build. Correct HTTP status codes allow standard monitoring and alerting tools to detect errors without parsing the body.

**Tradeoff / risk:** This is a **breaking change**. Any API consumer that pattern-matches on `"404 - bad request"` or assumes a 200 status on all responses will need to be updated. All downstream clients (mobile apps, dashboards, integrations) must be audited before this goes to production.

**Questions for team:**
- Which clients call `/compute`? Do we have a list?
- Can we run the new envelope format behind a version flag or new endpoint path to avoid a hard cutover?

---

### 4. Strict Input Validation (`validate_request`)
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** A new `validate_request()` function checks all required fields before any processing begins — country, lat/lon range, area, areaUnits, at least one recommendation flag, FCY bounds, and date format for PD/HD.

**Why it's better:** Currently, malformed inputs silently produce wrong outputs or cause opaque 500 errors deep in the processing code. With this change, bad requests are rejected early with a clear message telling the caller exactly what is wrong.

**Tradeoff / risk:** Stricter validation may reject requests that `main` currently accepts silently (e.g. a country sent as `"ng"` instead of `"NG"`, or an `areaUnits` value not in the allowed list). Any existing client sending slightly malformed data will start receiving 400 errors. Country casing is auto-corrected before the check, so that specific case is handled.

**Questions for team:**
- Should we add a transitional period where invalid inputs log a WARN but still proceed, before hard-rejecting?
- Are there known clients sending non-standard `areaUnits` values?

### 5. Translation System — SQLite + `tr()` Helper + Kinyarwanda
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** Replace inline translation table lookups with a `tr(key, lang, ...)` helper that reads from SQLite and supports named placeholder interpolation (e.g. `tr("cost_amount", lang, currency="NGN", amount="1200")`). Kinyarwanda (`rw`) is added as a supported locale. All hardcoded English strings in `process-FR.R`, `process-IC.R`, and `process-PP.R` are replaced with `tr()` calls.

**Why it's better:** Adding or editing a translation no longer requires touching R source code. Named placeholders make translation strings readable and safe to localise. A startup validator catches missing keys before the first request. Kinyarwanda support opens the door to Rwanda-specific deployments.

**Tradeoff / risk:** The `rectext` translation key (which contained raw R code fragments) is removed — if any code path still uses it, it will throw a `stop()`. The all-NA `rw` column was removed from the CSV then re-added properly to SQLite; old Rmd templates that read the CSV directly will no longer have an `rw` column to reference. All recommendation text output should be regression-tested against `main` to ensure no strings changed unintentionally.

**Questions for team:**
- Do we have Kinyarwanda translation content ready, or will `rw` fall back to English for now?
- Should the translation refresh be gated on the Kinyarwanda content being complete?

### 6. Structured Logging Module
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** A new `R/logging.R` module provides `log_write(level, ...)` with six levels (TRACE/DEBUG/INFO/SUCCESS/WARN/ERROR). Log level is controlled by `LOG_LEVEL` env var. Output goes to daily-rotating files in `logs/`. Incoming request bodies are logged at TRACE, results at DEBUG.

**Why it's better:** Currently there is no structured logging — errors surface only via R's `message()` / `warning()` to stderr or `print()` to stdout. With this module, log level filtering, file rotation, and JSON-serialised list output are all handled in one place. TRACE-level request logging makes it easy to replay a failing request.

**Tradeoff / risk:** TRACE-level logging writes the full POST body to disk. If requests contain PII (user coordinates, farmer data), TRACE logs must not be enabled in production without a data-handling review. Default is INFO, which does not log request bodies.

**Questions for team:**
- Confirm `LOG_LEVEL=INFO` as the production default.
- Should log files be rotated by the OS (logrotate) or is the daily filename suffix sufficient?

### 7. In-Memory Data Cache (`cached_read`)
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** Static data files (translations, dry-matter table, fertilizer NPK table, WLY_365 and soil_NPK-4 RDS files) are loaded once per server process and cached in an R environment. Subsequent requests read from memory rather than disk.

**Why it's better:** These files are read on every request in `main` but never change at runtime. Caching them eliminates repeated disk I/O and CSV parsing overhead — measurable on the 5 MB+ RDS files.

**Tradeoff / risk:** If a file on disk changes while the server is running (e.g. a manual data update), the server must be restarted to pick up the change. This is the expected behaviour for a long-running API process but should be documented for the ops team.

**Questions for team:** No blockers — recommend accepting as-is.

### 8. PP Yield-Class Threshold: 12.5 → 15 t/ha
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** In `process-PP.R`, the threshold that divides "low" from "high" yield class is changed from 12.5 to 15 t/ha to align with the soil-data breaks used in the underlying datasets.

**Why it's better:** The previous value was inconsistent with the soil-data model, meaning some farmers near the boundary received the wrong yield-class recommendation.

**Tradeoff / risk:** This directly changes recommendation output for farmers with FCY in the 12.5–15 range. The change is a correction, not a feature, but it should be validated against agronomic expectations before going live. Anyone who has seen the old output for that FCY range will notice a difference.

**Questions for team:**
- Can the agronomist/model owner confirm 15 is the correct boundary?
- Do we have test cases covering FCY values between 12.5 and 15?

### 9. Email Module Replacing SMS/Email (`sms_email.R`)
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** `R/sms_email.R` is deleted and replaced by `R/email.R`. The new module sends emails with PDF attachments generated by the WeasyPrint pipeline. SMS functionality is not carried over.

**Why it's better:** The new module is tightly integrated with the new PDF builders — each recommendation type generates its own PDF and attaches it independently. Failures in one attachment do not prevent others from being sent.

**Tradeoff / risk:** If SMS sending was still active in any production path, it is now silently removed. Anyone expecting SMS delivery will stop receiving messages with no error on the API side.

**Questions for team:**

- Do we need to preserve any SMS integration, or is email-only acceptable?

- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** The production deploy workflow now only triggers when files under `R/**`, `api.R`, `tests/**`, or `scripts/**` change. A `workflow_dispatch` trigger is also added so deployments can be kicked off manually from the GitHub UI without a code push.

**Why it's better:** Docs-only or asset-only commits no longer trigger a production deploy, reducing unnecessary downtime windows and deploy noise. Manual dispatch is useful for re-deploying after a server issue without making a dummy commit.

**Tradeoff / risk:** If a config file or `systemd/` change needs to go to production, it will no longer auto-deploy — someone must trigger manually. The path list needs to be kept up to date as the project structure evolves.

**Questions for team:**
- Should `systemd/**` and `.env.example` also be in the trigger path list?

### 11. Test Fixture Renaming
- [ ] Accept &nbsp;&nbsp; - [ ] Reject &nbsp;&nbsp; - [ ] Modify

**What it proposes:** All 29 existing test input files are renamed from `in_N.json` to descriptive names encoding the scenario (e.g. `in_1_TZ_FR_starch_factory_riskAtt0.json`). Six new edge-case fixtures are added, including a zero-price IC scenario.

**Tradeoff / risk:** Any external script, CI step, or documentation that references the old `in_N.json` filenames will break. The renaming is purely cosmetic for the test runner itself (filenames are glob-matched), but external references must be updated.
